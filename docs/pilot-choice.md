## 0 口径变更说明：旧口径为什么不再适用，新口径下结论有没有变

### 0.1 旧口径（已作废）

旧口径是“优先用户少、流量小、非主力，影响面最小”。它默认试点落地是正在跑的生产节点，试点动作可能打扰真实用户，所以要挑一个最不重要的。

### 0.2 旧口径为什么不再适用

用户 2026-11-22 补充：现在是开发阶段，没有正式运行，没有正式用户在跑，不用保护生产。“用户少、影响小、是不是主力”不再是选择标准，继续用它选会选错方向——它会把我们推向“最边缘、最久没动过、最难验证”的落地，而不是“最容易跑通”的落地。

### 0.3 新口径（现行）

选最有利于开发的那一个，优先级依次是：

1. **核心必须是 Xray**（agent 要 Xray stats 按人计量；sing-box 先只数总量，不能做 Phase 1 的归属验收）。
2. **到首个真实 QueryStats 计数器 + 首次推送的路径最短**：前置确认项最少、用户侧操作步数最少、改配置与重启的歧义最少。
3. **与后面开发和兼容主线的复用度最高**：试点走过的路（改配置、加回环映射、重启、验数、回滚）能原样复用到下一个 Xray 落地，推广时不再重新探路。
4. “能直接动手改配置、重启验证”：实话是**两个现成落地都做不到**——本 VM 没有任何落地机的 SSH 权限，任何一台的配置修改与容器重启都要用户在真机上动手。新建测试落地同样要用户动手 provisioning（机器、域名、证书、安装），只会更多、不会更少。所以这一项在现有条件下对三个候选都是“否”，差别只在用户侧操作量的多少，不构成“某台我能直接改”的区分。

### 0.4 新口径下结论有没有变

**结论已变，且变了两次，写清两次变化的原因：**

- 第一次（§0.2–§0.3）：旧口径“用户少、影响小”作废，改按“最有利于开发”选。新口径下决定性证据是核心类型（印尼落地 B 的 Xray 有服务器截图实证，智利落地 A 的核心无直接证据），当时初选印尼落地 B。
- 第二次（2026-11-22 05:01，用户亲口纠正）：**印尼落地 B 是客户定制，不得用于开发试点，直接排除。** 用户 05:00 已说智利落地可以用。于是试点改选智利落地 A。印尼落地 B 的 Xray 实证再充分也不改变这个结论——客户定制的节点不能拿来做开发试点，这是用户划的红线，不是技术判断。
- 一句话：初选印尼是技术判断，改选智利是用户拍板；技术判断服从用户拍板。

### 0.5 改选智利后的代价（先说清，不藏着）

改选智利落地 A 之后，之前印尼落地 B 的四条优势全部作废，试点要多走三步：① 先真机确认核心是 Xray（容器名 / 注册表，见 §6.1），确认前不能开工；② 同机两个节点，须先确认现行节点是哪个配置与容器，否则可能改错对象；③ 中转路径现故障待查，Phase 1 的归属验收第二步（中转 5MB 合并计 10MB）须等中转修好才能测。证书（DNS-01、到期 2027-02-16、无续签风险）是智利落地 A 唯一的确定性优势。**若真机确认智利落地 A 不是 Xray，停下来汇报，不要擅自换试点（不要擅自回印尼，也不要擅自新建）。**

### 2.2 第 1 项细说：核心是 Xray 还是 sing-box

**印尼落地 B：Xray，已确认。** 2026-11-16 用户发服务器截图，助手当场判定：服务端正常，证书已签出、443 在监听、xray 已正常启动，核心是 Xray xray-core，VLESS+WS，Caddy 终止 TLS 反代。2026-11-17 的记录补强：sing-box 明确**没有**装在印尼落地 B 所在的服务器上（当时用户在“替换 Xray / 换新服务器两个都留 / 同台明文临时测”三个方案里尚未拍板，且被提醒同台跑 sing-box 会因 80/443 被占而报错退出），此后无任何装机记录。直连链接在真机上可用（2026-11-21，小火箭 / v2rayNG 能用）。

**智利落地 A：倾向 Xray，但无直接证据，须真机确认。** 吻合 Xray 路径的点有三：① 协议是单协议 VLESS+WS+TLS（2026-11-20 订阅拉取核实：中转与直连同 UUID、同 WS 路径，只有 VLESS 一种）；② 自定义 HTTPS 端口 24443，Xray 安装脚本支持 `HTTPS_PORT` 自定义（`install.sh` 第 12 行注释、第 2346 行默认值 443）；③ DNS-01 证书，Xray 安装脚本的 `gen_compose_xray` 在 DNS 方式下用带 Cloudflare 插件的 Caddy 镜像且不绑 80（`install.sh` 第 553–590 行）。但这三点都不是排他证据：sing-box 安装脚本同样支持自定义 HTTPS 端口与 DNS-01，且 sing-box 的 VLESS 入站也能配成 VLESS+WS+TLS 单协议。面板侧也区分不了：落地记录只有 `Preset`（1=Xray、2=sing-box、3=自定义端口）与 `ModeNote`，24443 不属于预设 1（80/443）也不属于预设 2（80/443/8388/8443/8444），只说明它是自定义端口落地，不说明核心。**结论：智利落地 A 的核心在现有证据下是“无法核实”，不是“已确认 Xray”。**

为什么这一项是否决项：DEV-PLAN §3.2 与方案 v1 §2 要求 agent 读 Xray 的 `QueryStats`（按 `email` 分人）与 `AlterInbound`（增删用户）；sing-box 官方发布的二进制默认不带 Clash API / V2Ray API，且两个 API 都不是按用户的，sing-box 落地在 Phase 1 只能“先只数总量”（DEV-PLAN §3.9、§10.2），做不了归属验收（A 拉 5MB、B 拉 0MB，面板显示 A=5MB、B=0MB）。试点必须优先 Xray，且必须是**确认的** Xray，不是“大概是” Xray。

### 2.3 第 2 项细说：Xray 版本是否钉死

**三个候选现状一致：都没有钉死，且当前实际版本都无法核实。**

- 安装脚本层面：`install.sh` 第 535 行 Xray 用 `ghcr.io/xtls/xray-core:latest`，第 603 行 sing-box 用 `ghcr.io/sagernet/sing-box:latest`，都没有钉死版本。DEV-PLAN §3.2 要求“Xray 版本钉死 v26.x，升级前在测试环境跑一遍验收”，`docs/protocol-tracker.md` 也已把“落地 Xray 没钉死版本”记为阶段 0 发现的待确认问题，现状与要求不符。
- 方案调研时钉到 v26.11.9（方案 v1 §2.3），但那是调研时的版本，不是任何一台落地机上的实测版本。
- 对选择的影响：这一项不区分候选，但试点前必须定（DEV-PLAN §6 D3 之外的前置决策）：是把试点落地的安装脚本改成钉死版本，还是接受 latest 并在每次升级前跑验收。新建测试落地 C 在这一点上略好：可以在安装时就钉死，但现行脚本写死 latest，钉死仍须额外动作（改脚本或手动固定镜像版本），不是“新建就自动钉死”。

### 2.4 第 3 项细说：在线用户数 / 流量量级、是不是主力

**本项在新口径下只记录、不驱动决策；且结论是：两个现成落地都无法核实。**

面板侧按落地拆不出用户数与流量，原因在代码里：

- 落地记录 `Landing`（`panel/config.go` 第 114–141 行）只有地址、域名、证书域名、预设、模式备注、端口、名称、证书方式，**没有核心版本字段、没有用户数字段、没有流量字段**。
- 落地扩展状态 `LandingExt`（同文件第 51–72 行）只有落地级限流、到期、禁用、子节点，同样没有用户数。
- 用量是按订阅记的（`SubUser` / `MergedSub` 的限流、重置、`next_reset_at` 字段与 `user_traffic.json`，按订阅 id 做键），**不按落地记**；一个订阅跨多个落地时，面板无法直接说出“某落地有多少用户、在跑多少流量”。
- 面板“在线”探测只是 TCP 握手（`latency.go`），不是真实在线用户数。

能说的只有间接事实：2026-11-21 合并订阅拉取核实只有智利落地 A 的两个节点（中转 + 直连），说明智利落地 A 在合并订阅里被分发；印尼落地 B 的直连链接已交付用户（`your_files` 下有直连二维码存档）。两者真实在线用户数与流量量级：**无法核实**。新口径下这不影响选择，写在这里只是为了不把“不知道”说成“知道”。

### 2.5 第 4 项细说：证书方式与到期情况

- **智利落地 A：DNS-01，到期 2027-02-16。** 2026-11-18 晚用户真机验证：改名后卡片变智利、自定义端口 24443 的 DNS-01 落地证书显示剩余 89 天，中转/直连链接与二维码都正常。续签不走 80（面板 `util.go` 的 `renewModeFor`：DNS-01 一律自动；安装脚本 DNS 方式下 Caddy 不绑 80）。试点期间（数周）无续签风险。
- **印尼落地 B：无法核实，且已排除，不再确认。** 证书方式与到期日在任务给定信息、代码与记忆里均无记录；但该落地是客户定制、已排除，不再为它做真机确认。
- 对选择的影响：无——印尼落地 B 已排除，该段只作事实备查。

### 2.6 第 5 项细说：出问题的影响面

新口径下本项不驱动选择，但执行前仍须写明（DEV-PLAN 要求面板 UI 写明闪断，方案 v1 §5.2 亦然）：

- Phase 0：只加统计配置 + 重启 Xray 容器一次，不改 UUID、不改订阅链接、不执法。重启闪断约 1–2 秒（未实测，容器重启时间因机器而异）。
- Phase 1：只建两个测试订阅的每人 UUID，不迁真实用户。
- Phase 2：停用 = 删用户 + 重启 Xray，全节点用户闪断约 1–2 秒（原生 Xray 的 `RemoveUser` 不杀已建立的连接，无更优雅办法，方案 v1 §5.2；闪断时长未实测）。
- 影响人数：两个现成落地都无法核实（见 §2.4）。新口径下这不再是否决因素；开发阶段的闪断是可接受的，但每次重启前仍须告知用户一声，不要静默重启别人的节点。
- 智利落地 A 的额外未决项：中转路径目前不通（用户 2026-11-21 实测：中转不通、直连可用；助手侧探测两边 24443 TCP 均通、realm 在转发，故障点仍在中转机一段，待用户上中转机查 realm 状态、磁盘与监听）。这不阻塞 Phase 0（agent 推送不走中转），但会阻塞 Phase 1 的归属验收第二步（A 再走中转拉 5MB，面板应显示 A=10MB，不 double-count），除非中转先修好。印尼落地 B 无此未决项（直连已验证可用；其中转路径情况无法核实，但 Phase 0 不需要中转）。

### 2.7 第 6 项细说：与后面开发和兼容主线的关系

依据是 DEV-PLAN §10（2026-11-22 用户定稿的节点扩展与兼容设计）与方案 v1 §11：

- **§10.1 协议注册表**：新增节点类型只加注册项 + 适配器（三件套：入站配置模板、统计来源、停用方式），agent 主流程与面板核心表不动。VLESS+WS+TLS 在 Xray 上的三件套就是试点要验证的东西：入站模板（VLESS 入站 + WS 传输 + TLS，stats 开关默认开）、统计来源（Xray `QueryStats` 按用户）、停用方式（删用户 + 重启 Xray，闪断约 1–2 秒）。**智利落地 A 的试点直接产出这套注册表项**（确认 Xray 后），下一个 Xray 落地照抄；新建测试落地 C 产出的也是同一套，但它的安装路径是全新的，推广时仍须在现成落地补做 retrofit 验证。
- **§10.2 双核心并行**：Xray 与 sing-box 双核心并行，一台落地只装一种；Xray 是按人计量的主力，sing-box 先只数总量。试点选 Xray 落地，就是选主力路线；选 sing-box 落地（两个候选都不是已确认的 sing-box）只能验证总量模式，Phase 1 做不了。
- **回滚**：DEV-PLAN §3.8：Phase 0 → 现状只需停 agent、删 Xray 配置里的四块、重启容器；Phase 1 → Phase 0 只需删测试用户的 UUID。印尼落地 B 是标准单节点，配置文件与容器各一个（`config.json` / `tiktok-xray`），回滚目标唯一；智利落地 A 同机有两个节点（现行节点与待删的旧子域名节点），配置文件与容器各有两套，改配置与回滚时须先确认操作对象，回滚面更大，出错概率更高。
- **D10 前置条件与试点选择无关**：接口审计（`docs/interface-audit.md` §2–§3）确认面板 1.3.29 里 agent 要的三个新接口（拉用户表、推增量、下配置）一个都没有，panel-adapter 转接做不到推送，必须先拍板 D10（给面板加接口，发哪个版本）或接受不推荐的本地文件桥。选哪个落地都不改变这一点；试点落地定下来后，D10 仍是 Phase 0 推送落地的卡点，不要误以为“选了落地就能推数”。
